# SEADS Flight-Test-Log — operationalizes the Delight Test (Section 7)

> **The one question (SPEC §14):** *Does mouse-aim dogfight flying on a small sphere feel good?*
> Does energy management mean something? Does the mouse feel like War Thunder — the cursor commands,
> the plane obeys, nothing surprises you?

This log **is** the Section-7 gate. Harness numbers (settle, overshoot, sideslip, retention) are read
*alongside* the stars — they explain *why* a pass felt better; they are **never** pass/fail gates that
compete with the Human Delight Test (HARNESS §4/§8). The build + the first-principles ATs/invariants
stay green the whole phase; a tuning change that reds *those* is a bug, not a trade. **The GOLDENS are
different:** both load the live TOML, so any table edit MOVES them — that is the designed re-record
workflow (CLAUDE.md "A tuning pass = edit the table, re-run goldens, eyeball the diff"), not a
regression. Re-record **deliberately** each flight — never let it become reflex, because a golden's only
failure mode is blessing your bug (CLAUDE.md ## Learned). The gate.sh Stop hook will halt on a moved
golden by design: confirm the move was intended, re-record, move on.

## The discipline (do not deviate)

- **One knob per flight.** Change exactly one number in `config/aircraft.toml` or `config/controller.toml`,
  rebuild, fly, score. Two knobs at once and the log tells you nothing.
- **Hypothesis → Expected → Observed**, every row. Write the hypothesis *before* flying.
- **Tag builds your hands liked** — `git tag golden-NN-<why>`. Never lose a build that felt good.
- **Coefficients and gains only.** No architecture, no new mechanisms, no ruling changes (SPEC §15.7).
  CQ1/CQ2 are one-line data flips *only if the log shows the bias is felt* (SPEC §16).
- If **oscillation** reappears: raise `K_w` or lower `K_theta` — never anything else first — subject to
  the ZOH ceiling `K_w*sim_dt/I <= 0.5`; at the ceiling lower `K_theta` (past it, raising `K_w` *causes*
  the oscillation). (HARNESS §8 / SPEC §9)

## How to fly

Build then run the app (instructor mode is default):

```
cmake --build build --config Debug
./build/seads.exe
```

| Control | Action |
|---|---|
| **Mouse** | aim the cursor — the plane pursues it (the whole point) |
| **Space** (hold) | freelook — camera orbits, aim held in the world |
| **W / S** | pitch override (S = pull) — bypasses AoA/G, keeps authority |
| **A / D** | roll override (A = roll left) |
| **Q / E** | yaw override (Q = nose left) |
| **Left Shift / Ctrl** | throttle up / down |
| **F1** | toggle raw ↔ instructor mode (raw = device→Inputs, instructor off) |

Read telemetry alongside a flight when a score needs explaining:
`./build/seads_harness ctrl_fly [ticks] [out.csv]` (closed-loop max-rate turn, true-n column) and
`./build/seads_harness fly [ticks] [out.csv]` (raw plant).

## Objective instrument — the step tool (tuning-order steps 1–2)

`./build/seads_harness step [axis] [deg] [V] [ticks] [out.csv]` drives a pointing/bank step through the
**same closed loop the tests replay** (never a flat stub) and prints the three numbers the mantra turns
on — **settle time, overshoot, reversals** — all computed on the **total pointing error `t.e`**, the
*same signal AT-2 grades* (honest on every axis), plus the current gains and the ZOH margin. Numbers,
not vibes; still **never a gate** (AT-2 in `test_cascade.cpp` owns the pitch-step pass/fail).

- **`step pitch 30`** — the AT-2 scenario, the clean primary axis. Small step → outer-loop dominated
  (**`K_theta`**); large step (e.g. `pitch 60`) saturates the demand → the early rate response is the
  inner loop (**`K_w_pitch`** / **`K_wi_pitch`**). The workhorse for steps 1–2. (Sanity anchor: at the
  starting tables this reads settle ≈ 2.32 s, overshoot 0.28°, 2 reversals, steady 0.20° — an AT-2 pass.)
- **`step roll 60`** — lateral aim → bank-to-turn; the INNER block reads the roll rate (`K_w_roll`,
  `K_phi`). A big lateral step is a *sustained turn*, so its `t.e` holds a small residual (≈0.8°) and
  reads "did not settle" — that is honest, not ringing. Judge roll by **overshoot / reversals**.
- **`step yaw 4`** — small lateral pointing in FINE (`K_w_yaw`, `yaw_scale`). Coupled by nature — there
  is no pure-yaw maneuver on an aircraft; expect a residual steady `t.e` (rudder alone can't point).

**Step 1 (inner loop):** on this plant the inner loop is P-overdamped — raising `K_w` only adds damping
and the ZOH ceiling (`K_w*dt/I <= 0.50`) is hit before any proportional overshoot appears, so
`rate overshoot` stays **0.0% for every loadable `K_w`**. The knob that shapes inner-loop overshoot is
**`K_wi`** (the integral): raise `K_wi_axis` until `rate overshoot` shows a *slight* overshoot (a few %
— measured ~13.6% at `K_wi_pitch=2e6`), then back off 30%. Use `K_w` for damping headroom (keep ZOH
< 0.50), `K_wi` for the response shape.
**Step 2 (outer `K_theta`/`K_phi`):** raise until the pitch-step `overshoot`/`reversals` first break
AT-2 (>1.5° overshoot, or a limit cycle in reversals), then back off 30%; freeze the settle time as
`T_settle`. Note the loader caps `crit K_w/(4*I*K_theta) >= 1`, so `K_theta` cannot rise past
`K_w/(4*I)` — the tool prints `crit` and `ZOH`; a table that violates either won't load.

## Star rubric (1–5; ↓ = lower is better)

| Axis | 5 = delightful | 1 = broken |
|---|---|---|
| **Roll** | crisp, commands what you meant, stops where you point | sluggish or twitchy, overshoots the roll |
| **Pitch** | nose tracks the cursor, corner speed feels right | mushy or grabby; wrong "weight" |
| **Tracking** | pipper sits on a maneuvering target, no lag | lags, drifts, or rubber-bands |
| **Oscillation ↓** | dead calm at settle, no hunt | limit-cycles / buzzes / rings |
| **Transition** | push↔roll↔freelook handoffs invisible | dithers, snaps, or lurches at mode edges |
